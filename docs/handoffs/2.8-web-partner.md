## What was built
- **Venue Availability** (`ui/VenueAvailabilityPage.tsx`): list of my facilities (`facilities where partnerId == uid`), Add/Edit facility dialog (name, address, 6-digit postal code, capacity, amenities, latitude/longitude). "Find location" geocodes the postal code through the shared `MapProvider` (stub by default, OneMap with `VITE_MAP_PROVIDER=onemap`, optional `VITE_ONEMAP_TOKEN`); on `MAP_UNAVAILABLE` or no match the form says to type coordinates manually. Validation uses the shared `upsertFacilityInput` zod schema plus Singapore bounds; server field errors are shown via `fieldErrorsOf`.
- **Slots** (`ui/SlotPanel.tsx`, `SlotFormModal.tsx`): per-facility list grouped by day with status badges (Available / Unavailable / Under Maintenance / Booked), add, edit, remove (confirm). BOOKED slots show "Locked (booked)" with the explanation and have no edit/delete buttons; a server `SLOT_BOOKED_LOCKED` is also mapped to the same message. Client checks: required, end after start, future start, at most `MAX_SLOT_HOURS`. Moving an AVAILABLE slot off AVAILABLE shows a warning; the result notes how many requests were conflicted (`conflictedRequestIds`).
- **Venue Requests** (`ui/VenueRequestsPage.tsx`, `RequestDetail.tsx`, `DecisionDialogs.tsx`): "Needs your response" (PENDING and AWAITING_INFO, oldest first) and history tables (conflicted first). Detail shows workshop, instructor, venue, date, time, category, capacity, materials, info exchange and decision reason. Approve (confirm), Reject (optional reason), Request more info (message required, checked client-side). Reject and Request info offer an optional "suggest another slot" (other future AVAILABLE slots of the same facility, sent as `suggestedSlotId`). Actions only appear for PENDING (others get `REQUEST_NOT_PENDING`). `SLOT_CONFLICT` on approve and any CONFLICTED request show a warning with a link to Manage slots telling the partner to free up or add another slot so the instructor can re-request. List reloads after every decision.
- Layering: `ui -> controller -> repo`. Pure, unit-tested controller: `slotRules`, `facilityForm`, `requestRules`, `decisions` (callable injected), `venueErrors`, `addressLookup` (stub MapProvider), `mappers`. React hooks: `useLoad`, `useFacilities`, `useSlots`, `useVenueRequests`, `useGuardedAction` (logs out on `UNAUTHENTICATED`/`ACCOUNT_SUSPENDED`).
- Strings in `features/venues/strings.ts` (central strings untouched). The shared error strings (`strings.errors`) are used for all other codes; `SLOT_CONFLICT`, `SLOT_BOOKED_LOCKED`, `SLOT_OVERLAP`, `REQUEST_NOT_PENDING`, `NOT_FACILITY_OWNER` get venue-specific wording.

## Open issues
- Not exercised in a browser against the emulators (no manual run of add facility, slot CRUD, approve/conflict); only unit tests, typecheck and build. 3.1 should cover it.
- No DOM/component tests (Vitest is node-only).
- Slot "calendar" is a day-grouped list, not a month grid. Date inputs use the browser `datetime-local` in the browser's time zone (assumed Singapore).
- Data loads are one-shot (`getDocs`) with a Refresh button / reload after actions, not live listeners, so new requests need a refresh.
- Suggested slot cannot be offered for an already CONFLICTED request, since the server only accepts decisions on PENDING requests; the UI prompts the partner to add slots instead.
- The OneMap provider calls OneMap from the browser; CORS and token availability untested. The stub is the default.
- The map has no visual map/tiles; coordinates are numeric fields only.
- `useLoad` duplicates similar hooks in other features (each feature owns its own copy).
