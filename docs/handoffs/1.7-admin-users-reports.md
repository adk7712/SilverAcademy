- Check orders (the contract asserted in unit tests) are in each `decide*` doc comment. Notable choices: for `setAccountStatus` CANNOT_TARGET_ADMIN is checked before STALE_VERSION (do not leak version info of protected accounts) and REASON_REQUIRED before INVALID_TRANSITION.
- Admin cancel (one tx): workshop CANCELLED + `cancelReason`, CONFIRMED bookings -> CANCELLED and `seatsTaken` reduced by that count, ATTENDED bookings and `attendance` untouched, slot -> AVAILABLE (only if it is still booked for this workshop), pending venue request -> WITHDRAWN (when cancelling a PENDING_VENUE workshop), notifications to learners, assigned volunteers and the instructor. Volunteer assignments stay ASSIGNED. Archive never touches bookings/attendance; `UNARCHIVE` restores `statusBeforeArchive` (fallback COMPLETED).
- `ACTIVE_BOOKINGS_CONFIRM_REQUIRED`: CANCELLED whenever `seatsTaken > 0` (arch 4.7); ARCHIVED only for an upcoming OPEN workshop with `seatsTaken > 0`. `affectedBookings` in the output = bookings cancelled (0 for non-cancel actions).

## Open issues
- SUSPEND/REACTIVATE Auth step runs after the Firestore commit (cannot be in the tx). If it fails the call returns INTERNAL while `users.status` is already updated: `requireCaller` blocks the account anyway, but an existing ID token keeps passing Firestore rules until it expires (<= 1h) because rules read claims. A retry cannot re-run it (INVALID_TRANSITION); fix manually or add a repair callable.
- Admin edits of title/description/category do not update denormalised copies (`bookings.workshopSnapshot`, `venueRequests.workshopSummary`, workshop-derived notifications); bookings keep the title at booking time.
- Cancelling does not mark `volunteerAssignments` WITHDRAWN and does not refund anything (no points are earned before attendance).
- `incidentId` on `adminSetStatus` is only recorded in the audit details; existence is not validated. `submitReport` does not validate `relatedWorkshopId` / `relatedUserId` exist.
- `updateIncident` also accepts a text-only update (no `status`) on an open incident; empty updates are INVALID_INPUT. `updatePreferences` with a `lastMode` not held is INVALID_INPUT (`fieldErrors.lastMode`); the catalogue lists no error for it. Preferences do not bump `users.version`.
- `submitInstructorProfile` while already PENDING returns INVALID_TRANSITION (functions.md names no code for it).
- `reporterRole` on an incident = first of LEARNER, SENIOR_INSTRUCTOR, VOLUNTEER held by the caller (the input carries no active mode).
- I ran `prettier --write functions/src` once, which may have touched whitespace in other agents' files if they were unformatted (format:check passed before and after).
