# Handoff: 1.2 Booking transaction

## Task
All `bookings-*` callables in `docs/api/functions.md` §4: `bookings-bookWorkshop` (UC #2-2, transaction per architecture §4.1) and `bookings-getRoster` (UC #3-3 / SI class list). My Bookings / Digital Ticket (#2-3) are direct client reads by design (ADR-019), so there is no callable for them.

## Agent / model
Opus, 2026-10-19.

## What was built
- `decideBooking(workshopId, workshop, existingBooking, uid, now)`: pure. Checks run in the documented order: NOT_FOUND, CANNOT_BOOK_OWN_WORKSHOP, WORKSHOP_NOT_OPEN, WORKSHOP_STARTED (`startAt <= now`), ALREADY_BOOKED (any status, `details.bookingId`), WORKSHOP_FULL (`seatsTaken >= capacity`). Returns the snapshot, the new seat count and the seats remaining. If a workshop is OPEN but has no `startAt`, `endAt` or `venue` (inconsistent data), it is treated as WORKSHOP_NOT_OPEN.
- `generateTicketCode(random)`: 8 Crockford base32 chars from `crypto.randomBytes`. `byte % 32` is unbiased. Uniqueness within a workshop is probabilistic (40 bits) and not enforced.
- `createBooking` (repo): one `runTx` with reads of `workshops/{id}` and `bookings/{id}_{uid}`, then `decideBooking`, then `tx.create` of the booking (`ticketCode`, `signQr(bookingId)`, workshop snapshot with Timestamps), `tx.update` of `seatsTaken` and `updatedAt`, and `notifyTx` BOOKING_CONFIRMED (`refPath = bookings/{id}`). An AppError aborts every write.
- `decideRosterAccess` / `buildRoster`: the check order is NOT_FOUND, then allow ADMIN, the owning SI or an ASSIGNED volunteer. Otherwise a caller holding VOLUNTEER gets NOT_ASSIGNED and anyone else gets PERMISSION_DENIED. The output lists only CONFIRMED and ATTENDED learners, sorted by name, and never includes `qrPayload`. Only ASSIGNED volunteers are listed. Reads are plain, with no transaction.
- Handlers follow the 1.1 recipe (`defineCallable`; plain `bookWorkshop` / `getRoster` functions are exported for tests).

## Open issues
- **No audit entry for bookings.** functions.md does not require one, and `AUDIT_ACTIONS` has no booking action. Adding one would need a change in shared.
- Under very high contention, a booking can exhaust `TX_MAX_ATTEMPTS` (5) and get BUSY_TRY_AGAIN. This did not happen with 20 parallel calls on the emulator.
- Ticket code collisions within a workshop are not checked. Task 1.3 already plans `>1 match -> TICKET_NOT_FOUND`.
- The `bookings (workshopId, status in [...])` roster query relies on the existing composite index.

## Notes for next agent
- 1.3 attendance: the booking's `qrPayload` comes from `signQr(bookingId)`; use `verifyQr`. Set `bookings.status = 'ATTENDED'` and `attendedAt` so the roster shows them.
- 1.5 admin cancel (§4.7) must set bookings to CANCELLED. The roster then hides them, and `decideBooking` still returns ALREADY_BOOKED for that learner. Rebooking a cancelled workshop is not possible anyway, because its status is not OPEN.
- `workshops-adminUpdateWorkshop` may lower capacity only down to `seatsTaken`. `decideBooking` treats `seatsTaken > capacity` as full regardless.
