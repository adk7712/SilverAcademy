# Handoff: 1.5 Workshop CRUD, venue request/approval, volunteer opt-in

## Task
Callables for workshop create/update, venue facilities and slots, venue requests with approval (slot locking), and volunteer opt-in/withdraw (UC #1-2, #1-3, #3-2, #4-1, #4-2).

## Agent / model
Sonnet, 2026-10-19.

## What was built
- **workshops** (`functions/src/workshops/`): `workshops-createWorkshop` (approved profile, creates DRAFT), `workshops-updateWorkshop` (owner, DRAFT only, merged volunteer rule re-checked), `workshops-optInVolunteer`, `workshops-withdrawVolunteer`. Pure rules: `controller/decideWorkshop.ts`, `controller/decideVolunteer.ts`; txs: `repo/workshopRepo.ts`, `repo/volunteerRepo.ts`.
- **venues** (`functions/src/venues/`): all 7 callables in functions.md section 6. Pure rules: `decideFacility`, `decideSlot`, `decideVenueRequest` (request / respond / withdraw), `decideVenueDecision` (approve / reject / request info), `conflicts` (planConflicts). Txs: `facilityRepo`, `slotRepo`, `venueRequestRepo`, `decisionRepo`, `conflictsRepo`.
- "Submit", "list my", "get" workshops, volunteer opportunities list and assigned list, venue browse and CP queues are direct Firestore reads (functions.md, architecture 2.5/3.4), so no callable exists for them. `submit` = `venues-requestVenue`.
- Approval (`venues-decideVenueRequest`, APPROVE): one tx sets request APPROVED, slot BOOKED (+`bookedWorkshopId/RequestId`), workshop OPEN with `slotId/startAt/endAt/venue`, every other PENDING/AWAITING_INFO request on the slot CONFLICTED with its workshop back to DRAFT, and notifications. Reject: `reason` optional, workshop back to DRAFT. Request info: `message` required (REASON_REQUIRED).
- Volunteer opt-in: assignment id `${workshopId}_${uid}` (`tx.set`, reuses a WITHDRAWN doc) + `volunteersAssigned` counter in one tx; duplicates give ALREADY_OPTED_IN `{status}`.

## Interfaces exposed
- Callables `workshops-{createWorkshop,updateWorkshop,optInVolunteer,withdrawVolunteer}` and `venues-{upsertFacility,upsertSlot,deleteSlot,requestVenue,decideVenueRequest,respondToInfoRequest,withdrawVenueRequest}`.
- `venues-decideVenueRequest` APPROVE conflict path: commits request CONFLICTED (workshop to DRAFT, SI notified), then throws `SLOT_CONFLICT` `{requestId}`. A request that a concurrent approval already made CONFLICTED and is then approved again also gives `SLOT_CONFLICT` (not REQUEST_NOT_PENDING), so the CP UI always prompts for an alternative. REJECT/REQUEST_INFO on a CONFLICTED request is REQUEST_NOT_PENDING.
- `venues-upsertSlot` conflicts open requests when an AVAILABLE slot becomes UNAVAILABLE/MAINTENANCE or its times change (architecture only says "leaves AVAILABLE"; moved times added because requests snapshot the slot times). `venues-deleteSlot` conflicts them too. Both return `conflictedRequestIds`.
- Notification types used: `VENUE_REQUEST_NEW` (to CP), `VENUE_REQUEST_DECIDED` / `VENUE_REQUEST_INFO` / `VENUE_REQUEST_CONFLICTED` (to SI). The SI reply to an info request notifies the CP with `VENUE_REQUEST_INFO` (no dedicated type exists).
- No audit entries are written (functions.md lists none for these callables).

## Open issues
- `requestVenue` requires slot start > now + `VENUE_REQUEST_MIN_LEAD_MIN` (60 min); approval does not re-check the slot time (architecture 4.6 lists no such check), so a CP could approve an already-started slot.
- Facility capacity edits do not re-validate existing requests/workshops.
- `upsertSlot` overlap query uses a single-field `startAt` range (no new index) and assumes slots are at most `MAX_SLOT_HOURS` long.
- Emulator tests need ports 8080/9099/9199/4400 free; stray `java` Firestore emulators from crashed runs (parent pid 1) make `npm run test:emulator` fail with "port taken" and must be killed.
